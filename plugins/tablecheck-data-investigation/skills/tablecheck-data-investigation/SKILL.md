# 前提

- APIの1行がTableCheckの1予約とは限らず、来店予定内訳やコピー予約が複数レコードになる可能性を考える。
- 画面表示、CSV、APIレスポンスを同じ日付・同じ予約識別子で比較する。
- 「確認済」「打合せ中」「お会計済み」などのステータスは、表示条件と画面上の表示値を分けて扱う。

# 手順

1. 対象日、グループ名、予約ID、店舗、会場、時刻を記録する。
2. TableCheck管理画面の予約詳細、CSV、APIレスポンスを保存し、同じ予約を突合する。
3. `reservation_id`、グループ名、コピー元予約、来店予定配列、ステータス、フラグ、テーブル、店舗名を比較する。
4. 表示条件は要件として明示し、必要なら来店予定内のステータスが「確認済」のレコードだけを採用する。
5. 「お会計済み」や「打合せ中」は検証対象として残すが、表示対象に含めるかは勝手に拡張しない。
6. 会場が数値だけの場合は、店舗・スラッグ・会場場所設定など代替項目の優先順位を定義する。
7. APIに存在しない終了時刻や担当者は推測せず、利用時間から算出する場合は算出値であることを明示する。

# 注意点

- APIレスポンスのフィールド名は実データで確認し、推測したフィールド名を本番処理に追加しない。
- フラグのハッシュや内部識別子は表示から除外できるが、調査用の元データは改変しない。
- 顧客名・電話番号・メールアドレスを共有ログやコミットに残さない。
