name: authenticated-save-verification
description: Web画面の保存・更新・削除が実際の認証付き環境で成功し、再表示後も永続化されていることを確認するときに使う。
---

# 前提

- 保存確認は、画面表示やビルド成功だけで完了としない。
- テスト用アカウント、テスト用データ、対象環境を明確にし、本番データを不用意に変更しない。
- APIパス、HTTPメソッド、認証方式、権限、保存先、プロキシ経路を確認する。

# 手順

1. 対象画面で入力前の状態を確認し、テストデータを一意に識別できる値にする。
2. ブラウザのNetworkログで、保存ボタンが送信した正確なURL、HTTPメソッド、ステータス、レスポンスを確認する。
3. 失敗時は次の順で切り分ける。
   - DNS・TLS・接続切断
   - CDN・リバースプロキシ・WAFの遮断
   - 認証切れや権限不足
   - 入力検証エラー
   - APIルート不一致
   - DB接続・制約・処理例外
4. API名にドット、拡張子に似た末尾、特殊文字などが含まれる場合、プロキシやWAFの禁止パターンとの衝突を確認する。
5. 成功レスポンスを確認した後、画面を再読み込みし、保存した値がAPIから再取得されることを確認する。
6. 更新・削除では、別画面または再検索でも結果が反映されていることを確認する。
7. 未認証要求が拒否されること、対象外ユーザーが操作できないこと、既存の保護設定が維持されていることを確認する。
8. 確認結果を、対象環境、操作、API結果、再表示結果、残課題に分けて記録する。

# 注意点

- `Failed to fetch`をキャッシュ、サービスワーカー、ユーザー操作の問題と決めつけない。ブラウザ、プロキシ、アプリログを突き合わせる。
- 保護設定を全面解除したり、認証を無効化したりして回避しない。必要なら対象APIだけを最小範囲で許可する。
- テストデータを作成した場合は、削除可否と削除方法を事前に確認する。
- トークン、Cookie、パスワード、個人情報をログ・スクリーンショット・共有資料に残さない。
