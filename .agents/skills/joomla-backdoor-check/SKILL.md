# Joomla バックドア調査スキル

Joomlaサイト(ファイル一式のローカルコピー + DBダンプ)を対象に、改ざん・バックドア・webシェルの有無を体系的に調査する手順。本番に一切手を触れず、ローカル/隔離環境で完結させる。

## 前提

- 調査対象サイトのファイル一式(ドキュメントルート)がローカルまたはアクセス可能な場所にあること(FTP等で取得)
- データベースのダンプ(.sqlまたは.sql.gz)が入手できていること
- 「駆除作業前」なのか「駆除作業後」なのか、依頼者に必ず確認する(調査結果の意味合いが変わるため)

## 手順

### 1. 正確なJoomlaバージョンを特定する

`administrator/manifests/files/joomla.xml` 内の `<version>` タグを読む。これが公式クリーン版と比較する際の基準バージョンになる。

### 2. 公式クリーン版を取得する

クラウド側のBashツールで、対象バージョンの公式フルパッケージをダウンロード・展開する:

```
curl -sL -o joomla.zip "https://github.com/joomla/joomla-cms/releases/download/{VERSION}/Joomla_{VERSION}-Stable-Full_Package.zip"
unzip -q joomla.zip -d src
```

これが改ざんされていないリファレンスになる。

### 3. コアディレクトリのファイル一覧比較

以下のコアディレクトリを対象に、実ファイル一覧(パス・サイズ)とリファレンスを突き合わせる:

 administrator, bin, cli, includes, language, layouts, libraries, media, modules, plugins, ルート直下のphpファイル

`components` はコアコンポーネントのみ対象(com_admin, com_content, com_users 等の既知のコア一覧と照合し、サードパーティ製 com_* は対象外)。`templates` はカスタムテンプレートのため比較対象外(ただし手順5の観点は適用)。

洗い出す差分:
- a) 公式にはないがローカルにのみ存在するファイル(最重要 — バックドア/webshellの可能性)
- b) 公式にはあるがローカルにないファイル(削除・改変の痕跡の可能性、パッチレベル差でも起きる)
- c) 同じパスでサイズが異なるファイル(内容改変の可能性)

ディレクトリが大きくトークン上限を超える場合、ツールが自動保存したファイルをBashでパースして集計する(生の一覧を全部会話に出力しない)。この機械的な突き合わせ作業は、メインの会話コンテキストを圧迫しないようサブエージェントに委譲し、要点だけ報告させるとよい。

### 4. 疑わしいファイルの内容確認

手順3で見つかった差分ファイルのうち、見慣れない名前・場所にあるものをステージングして中身を読み、以下のパターンを探す:

- `eval(`, `base64_decode(`, `gzinflate(`, `gzuncompress(`, `str_rot13(`, `assert(`, `create_function(`, `preg_replace(...'/e'`
- `$_POST` / `$_GET` / `$_REQUEST` を使った動的コード実行(`call_user_func`、変数関数呼び出し `$x($y)` など)
- 極端に難読化された変数名・意味不明な短いコード

### 5. 書き込み可能ディレクトリのPHPファイル捜索

`images`, `media`, `tmp`, `cache`, `log` を再帰的に調べ、`.php` ファイルを全て洗い出す。Joomla標準の保護用ダミーファイル(`die('Forbidden.')`のみ)以外の.phpがあれば要注意。

### 6. データベース側の監査

DBダンプをローカルでzcat展開し、grep/awk/pythonで以下を確認する(全文をコンテキストに読み込まず、抽出・集計のみ行う):

- `#__users` + `#__user_usergroup_map`: Super User/Administratorグループのアカウント一覧を出し、依頼者に見覚えのないアカウントがないか確認してもらう
- `#__extensions`: type別(plugin/component/module/template)に一覧化し、不審な名前の拡張機能がないか確認する
- `#__content` 等のコンテンツテーブル: `<iframe`, `<script src=` の埋め込み先ドメインを抽出し、既知の正規サービス(YouTube, Googleマップ等)以外がないか確認する
- 難読化パターン(`eval(`, `base64_decode` 等)がDB全体に含まれていないか件数を確認する

### 7. 結論と報告

以下を簡潔にまとめる:
- 比較したディレクトリ・ファイル数
- a)b)c)それぞれの該当件数と、重要なものは具体的なパス
- 内容確認で断定できたマルウェア/webshellがあれば詳細
- 管理者アカウント一覧(依頼者への確認事項として)
- 総合所見(改ざんの痕跡があるかないか、はっきり結論づける)
- 気づいた副次的な問題点(例: DBダンプを公開領域に置きっぱなし、不要な旧バックアップフォルダの残存など)

## 注意点

- この調査はファイル・DBの中身ベース。サーバーのアクセスログやホスティング側のcron設定は別途ホスティング事業者に確認する必要があることを、報告時に必ず明記する
- 「駆除作業を実施済み」という依頼者の申告を鵜呑みにせず、必ず独立した観点で検証する
